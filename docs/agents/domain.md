# Domain Docs

Как инженерные скилы должны потреблять доменную документацию этого репозитория при исследовании
кода. Раскладка — одноконтекстная (single-context).

## Перед исследованием прочитай

- **`GLOSSARY.md`** в корне репозитория.
- **`docs/adr/`**: ADR, затрагивающие ту область, в которой собираешься работать.

Если каких-то из этих файлов нет — **продолжай молча**. Не сообщай об их отсутствии и не предлагай
создать их заранее. Скил `/domain-modeling` (доступен через `/grill-with-docs` и
`/improve-codebase-architecture`) создаёт их лениво, когда термины или решения действительно
устаканились.

`GLOSSARY-MAP.md` в этом репозитории не нужен: отдельные контексты не выделяются, `backend/` и
`frontend/` — части одного домена.

## Структура файлов

```
/
├── GLOSSARY.md
├── docs/adr/
│   └── 0001-<название-решения>.md
├── backend/
└── frontend/
```

## Используй словарь глоссария

Когда в твоём выводе появляется доменное понятие (в заголовке issue, предложении по рефакторингу,
гипотезе, имени теста) — используй термин так, как он определён в `GLOSSARY.md`. Не уходи
к синонимам, которых глоссарий явно избегает.

Если нужного понятия в глоссарии ещё нет — это сигнал: либо ты изобретаешь язык, которого в проекте
нет (передумай), либо есть реальный пробел (отметь его для `/domain-modeling`).

## Отмечай конфликты с ADR

Если твой вывод противоречит существующему ADR — скажи об этом явно, а не переопределяй молча:

> _Противоречит ADR-0007 (событийная модель заказов), но стоит переоткрыть, потому что…_
